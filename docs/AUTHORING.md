# Authoring lessons — the API

How to write a lesson, a beat and a picture. The rules of *what* to write
are in [PEDAGOGY.md](PEDAGOGY.md); this is *how*, as built. Written by the
two foundation workstreams (F1: the beat engine and the bubble; F2: the
stage pictures) and kept in step with the code. The invariants these rest
on (a lesson's progress is derived, the beat index is view state, a
picture is the evidence drawn) are CLAUDE.md's 11 and 26.

The lessons today: the warm-up's `meet`, `types`, `choose`,
`operations`; Stage 1's `names`, `order`, `s1-ideas` and `wake` (the one
editor lesson); `s2-ideas` … `s8-ideas`, each stage's ideas as a console
lesson; and `decide` (Making Choices), played between `s5-ideas` and
Stage 5's sets. Each file's header says what it teaches and why it is
shaped the way it is — read one before writing the next.

## The beat engine (content/lessons/core.ts)

IMPORTS. Lesson files import from './core' (not './index', which imports them, so that would be a cycle). Everyone else imports '../../content/lessons' (index.ts re-exports all of core plus LESSONS). Register a new lesson in content/lessons/index.ts (import it, add `[x.id]: x` to LESSONS, re-export it). The helpers core exports: heard, was, worked, ever, everBy, points, sameObject, targetOf, errorType, stopped, bareWord, commaDecimal, boolMiss, countMiss(line, things), measureMiss, wordsMiss(line, example), cap, digits. numberOf, boolOf and textOf still come from '../../src/scene/props'. The speaker names are in content/cast.ts: CROW_NAME = 'Corvid', and SPEAKERS = { crow: {name: CROW_NAME, colour:'--ink'}, robot: {name:'Robot', colour:'--brand-deep'}, courier: {name:'Mira', colour:'--mira'} }. Write '{CROW_NAME}' inside any line and script() fills in the name. Never write where the console is ('on the right'): on a phone the panels stack and it is below the stage. Write '{CONSOLE}' and script() fills in 'on the right' side by side or 'below' stacked (CONSOLE_WHERE in core.ts; the Workbench passes the layout).

TYPES (core.ts):
type CastAction = { actor: string; do: 'enter'|'hide'|'wave'|'hop'|'sleep'|'wake' }
type Focus = 'console'|'memory'|'run'
type Beat = { say: string; speaker?: string /*actor id, crow if omitted*/; show?: Prop; thought?: string; act?: CastAction[]; focus?: Focus }
type LessonStep = { say: string /*THE ASK only (R3)*/; speaker?: string; done: (e: Evidence)=>boolean; show?: Prop; ask?: string; nudge?: (l: Line)=>string|undefined; beats?: Beat[]; praise?: string | ((answer: Heard|null)=>string); tag?: 'you'|'robot' }
type Lesson = { id; teaches: string[]; steps: LessonStep[]; outro: string | Beat[]; outroSpeaker?: string; ordered?: boolean; finale?: Prop; takeaway?: string }
type ScriptItem = { kind: 'praise'|'beat'|'ask'|'reply'|'outro'; asking: boolean; text; speaker?; show?; thought?; act?; focus?; tag?; beat?: number }
type Script = { at: number; before: number; finished: boolean; items: ScriptItem[]; rest: number }

EVIDENCE. `Evidence = { snapshot; thoughts: Heard[]; history: MemorySnapshot[]; lines?: { source, memory }[]; last?: Line }`. `history` is memory after each accepted line plus memory now; `lines` is the same accepted lines, each beside the source that made it (a practice exercise's setup lines are one entry, joined). `ever(e, s => …)` asks whether memory ever held something; `everBy(e, (source, s) => …)` asks whether an accepted line whose source passes made it hold. Use `everBy` when a step is about *how* memory changed, not only what it holds: memory alone cannot tell `ride = "van"` typed bare from the same line inside an `if` block, so Making Choices' if step is `everBy(e, (src, s) => /^\s*if\b/m.test(src) && points(s, 'ride', "'van'") …)` and its else step also wants an `else` header. Both stay true once true (lines are only added) and are derived from the accepted history the workbench already keeps; nothing is stored. With no `lines` (evidence built by hand without sources), `everBy` holds of nothing, so a unit test of such a step must hand it `lines`. Pair such a step with a `nudge` for the shortcut (decide.ts: 'Let the robot decide: put that line inside an `if`.').

script(lesson, evidence) is pure and derived. For step `at`, items are: [praise of step at-1, if that step has one] + one item per beat of step at + the ask. The ask becomes kind 'reply' (the nudge's text) while a miss applies, in the same position. A miss is a line that did not move the lesson: `beforeLast(evidence)` takes the last line back out (its thought, and its memory entry, which the workbench hands over as `Line.memory`), so a binding that did a step (`x = 10`) is never answered as a miss to the step after it. Once finished, items are [praise of the last step, if it has one] + the outro (a string outro counts as one beat). `rest` is the last index: the ask, or the final outro line. The praise stays in the list for as long as the player is on step at, so the list never shifts under the index. A praise function receives the thought that did the step (exact in an ordered lesson). Praise is always spoken by the crow. guidance(lesson, e) = { text, speaker } of items[rest], as before. A lesson with no beats, no praise and a string outro has exactly one item and behaves as it did before this change.

staging(lesson, e, beat?) (beat is an index into items; defaults to rest). While a beat shows, the picture is the latest `show` at or before that beat, falling back to the step's `show`, or to `finale` once finished. A beat picture's key is `${id}:${at}:b${i}` only when it differs from the step's picture, so a picture shared across beats stays the same element. The ask brings the step picture back under key `${id}:${at}`, with its `ask` text under it, and a miss is drawn in only on the ask or reply. During praise the answered picture stays on screen (key `${id}:${at-1}`, verdict 'right', answer drawn in, no question under it). After a praise, nothing plays a 'leaving' animation; without a praise, leaving works as before.

castAt(lesson, e, beat?) → { hidden, asleep, acting }. An actor whose first action anywhere in the lesson is 'enter' stays off stage until that beat (e.g. Mira in the types and choose scenes: the courier actor is always in the scene spec). 'hide' sends an actor off again. sleep/wake persist (the robot's screen goes dark or lights up). wave/hop play only while their beat is showing. Everything is folded from all beats of earlier steps plus the current items up to the index, so Back and resuming a level both give the right cast.

HOW IT RENDERS. Beats, praise and outro items are narration: the console is disabled with the placeholder 'Listening… press Next'. A big Next button sits bottom-centre with a small ◂ Back beside it. Enter or Space anywhere advances; the first press finishes the typing and the second moves on. A thin bar of steps runs along the top of the stage. At the ask or a reply the console is enabled, focused and glowing; Next is hidden; the console's own prompt says where the answer goes (there is no pointer on the stage). Everything on the stage's bottom edge (Next, the takeaway, Continue) is lifted above the scene's hint strip when it shows. The bubble's name pill shows the speaker's colour; the tag appears as a 'You answer' or 'Robot works it out' pill on the ask; a reply has a soft amber tint, never red. Text types on at about 45 chars/s, pausing at , ; : . ! ? (never at one between two digits, so `2.8` types on whole), with `code` chips appearing whole. A beat's `thought` shows in the robot's cloud during that beat only (`''` empties it); it is never evidence. Otherwise the cloud shows the robot's newest real thought only while it belongs to what is being told (`cloud` in core.ts): one thought since this step began, or the answer while its praise is read. On the next item after a praise it clears, so an old answer never stands over the next question, and a line that stopped the robot empties it (a beat's own `thought` still shows). On a phone the takeaway stands at the top of the stage, under the step bar, not over the cast. `focus` pulses the console, the memory pane or the Run button. On a stacked layout (a phone) focus 'memory' also scrolls the page just far enough to show memory's first rows, and back to where it was when the beat moves on, so 'Look below' always has memory on screen. Once finished and resting on the last outro line, the takeaway bar shows with Replay (which jumps back to the first outro beat), and the console opens again. Continue (.advance) shows only once the lesson is finished *and* resting on the last outro line (`done && !listening` in ScenePanel; invariant 10), so it arrives with the takeaway and never sits beside Next. A browser journey that wants Continue must walk (or `skip()`) to the last outro line first. Keep each beat or praise line to 110 characters or fewer: tests/unit/lessons/every.test.ts enforces this for every lesson.

THE BEAT INDEX is the workbench's only piece of lesson view state: an index into script().items, keyed on `${activity}:${step}`, so it goes back to 0 whenever the step changes and on remount, and is never stored or checked. Returning to a level resumes at the derived step and replays its beats. Where the cloud's telling began (`CloudFrom`) is taken the same way, when the step changes. Nothing a lesson file writes can reach either.

TYPING BLOCKS. The console takes a block (`if`, `for`, `def`) over several lines and runs it as one accepted line when a blank line closes it. It indents the way an editor does (src/repl/indent.ts): Enter after a line ending in `:` starts the next line four spaces in, a body line keeps its indent, Tab adds four, Backspace in the indent takes four back, and a line of indent alone counts as the blank line that closes the block. Outside a block Tab still moves focus; inside one, Escape hands it back. So an ask that wants a block names the header, the body "indented", and "then a blank line" (decide.ts: 'Type `if weight > 10:`, then `ride = "van"` indented under it, then a blank line.'), and a beat before the first block says how (s5ideas, decide). A browser journey typing a block key by key types only the *difference* from the automatic indent, with Backspace to dedent before an `else:` (lesson-decide.spec.ts's `block`); `window.botgineer.say(source)` with the whole block as one string does not go through the keys. The memory a block leaves is one entry in `history` and `lines`, with the whole block as its source.

MULTIPLE CHOICE. A step with `choices: { id, options: [{ id, label }], answer, nudge? }` is answered by picking on the stage, not by typing to the robot: while it asks, the console is closed and the options stand bottom-centre where Next stands during narration (`Options` in ScenePanel, lettered A, B, C…: numbers read as indexes in a question about a list; shown in an order hashed from the question, so the key is not always first; answered by a click only, nothing focused, so neither a focus ring nor Enter picks one). Its `done` is `(e) => chose(e, choices)`, judged on `Evidence.picks` (every pick, oldest first; only grows). A wrong pick is answered by `nudge(choice)` (or 'Not that one. Try another.') as a reply in the ask's place, and stays on the row marked tried (`ScriptItem.choices.tried`) so the next try is among the rest. `id` must be unique in the lesson. Option ids `bool`/`int`/`float`/`str` wear their type's colour. In an ordered lesson a choice step consumes no thought. `v2/types.ts` builds its quiz this way, from a seed (`?seed=` in the address fixes it for a test). Journeys pick with `window.botgineer.choose(id)` or by clicking `choice-<id>`; `beat()` reports `choices` and `tried`.

EDITOR LESSONS (v2: `v2-if`, `v2-loops`). An activity with `mode: 'editor'`, `version: 2` and a lesson is judged on its *runs*, the way a console lesson is judged on its lines: each Run of the player's program adds a `Run` to `evidence.runs` (`{ source, ok, raised, line, ran, final, cases }` — `raised` is the exception's type name, or `'steps'` for a loop that never finished; `ran` is every line reached, once per visit) and the same `{ source, memory: final }` to `lines`, so `ever`, `everBy` and `reached` work unchanged; `evidence.last` is the run as a `Line`, with `run` on it for replies. The narration closes the editor (read only, Run off) the way it closes the console. Four additions: `Beat.code` puts the crow's program in the editor in place of the player's (framed as the crow's; what it adds to the beat before's code types itself in); `Beat.run` shows one moment of a real, quiet run of that code — `{ line, pass? }` is memory just after `line` ran for the `pass`-th time, that line lit and what had run ticked, and `'end'` is the whole run with the lines it never reached dimmed (the picture of an `if`'s skipped block) — drawn in memory as the crow's; `LessonStep.code` hands the player a program when the question is reached (once per visit; omitted, they keep theirs, so steps can build one program); and `LessonStep.cases` makes the robot try the program again on each case after every Run (`withCase` swaps each name's first top-level assignment), recorded on the run. Judge a program on what it *does* across its cases plus the shape the step is about, with `content/lessons/v2/code.ts`: `decides(e, shape, name, want)`, `wrongCase(line, name, want)` for the reply naming the case that came out wrong, `codeMiss(line)` for the usual stops (a header without `:`, `else if`, one `=` in a question, a block not pushed in, a word without quotes, a loop that never finished), `valueOf(snapshot, name)` (a list by its items), and `caseRows` for the `cases` picture. A `want` must tolerate another step's case names (it may throw; `decides` treats that as not this step's). Test surface: `send(program)` skips the narration, puts the program in and Runs it, resolving once the run and its cases are in.

MEMORY AFTER A FAILED LINE. The console always shows the last accepted memory, including after a line that failed (a failed line is never kept, so the robot lost nothing). A beat with focus 'memory' after a miss therefore points at what is really there.

SLOT LABELS. Every arrow out of a list or dict carries its index or key, always (graphLayout.ts, "Slot labels"). A beat may point at them ("slot `0` points at…") without asking the player to pick a card first.

WRITING A UNIT TEST: put it in tests/unit/lessons/<id>.test.ts and import { line, failed, typed, th, over, snap, bound, value, NOTHING, EMPTY } from './fixtures'. A step judged with `everBy` needs evidence that carries `lines` (each accepted line's source beside its memory); fixtures built without them make `everBy` hold of nothing (decide.test.ts builds its own). Examples: progress(lesson, typed(line('True', th('bool','True')))); script(lesson, typed(failed('seven','NameError'))).items[s.rest].kind === 'reply'; staging(lesson, NOTHING, 1).current.key; castAt(lesson, NOTHING, 0).hidden. Every registered lesson is also checked automatically by every.test.ts, and every.test.ts also checks that every lesson named by an activity is registered, and vice versa.

WRITING A BROWSER JOURNEY: put it in tests/browser/lesson-<id>.spec.ts and import { open, say, skip, beat, send, reprs, targetOf, seedProgress, WARM_UP, OPS, speechSettled, EDITOR } from './helpers'. say(page, line) skips narration first, then types into the console and waits until the robot is no longer busy. beat(page) returns { at, of, text, asking, speaker, kind, listening }. To walk the beats, call page.evaluate(() => window.botgineer.next()) (next() advances without waiting for the typing) or click getByTestId('beat-next'). Test ids: guide (data-kind, data-speaker), speaker-name, ask-tag, beat-next, beat-back, beat-bar, takeaway, replay, instrument (data-focus, class glow), actor-<id> (data-offstage, data-asleep, data-look), console-input. Call speechSettled(page) before measuring the bubble after a speaker change. window.botgineer.say(line) also skips narration.

PLACEHOLDERS to replace: meet.ts (it doubles as the engine demo; beats.spec.ts depends only on its shape — it must have several beats before an ask, a demo thought, a robot sleep/wake, a beat with focus 'console', a step praise, outro beats and a takeaway, all of which §5 already has), types.ts (it must keep teaching bool/int/float/str/kind; add 'char' only once concepts.ts has it), choose.ts, and wake.ts (editor mode: finishing must match the bay's watches exactly, so its last step's done is awake(), the bay's own verdict. The editor reports no line, so there is no nudge; a name set to the wrong kind, which the hint strip no longer lists as missing, is named by the steps before it instead: one per fixture, each done when that watch alone is satisfied, so the ask on show names the first fixture still wrong).

## Stage pictures (src/scene/props.ts)

Import `type Prop` from 'src/scene/props'. Put a Prop in a Beat's or a LessonStep's `show`. What the robot answered is drawn into the current picture automatically (PropView.answer, verdict, heard). Colours are one per kind: --k-bool, --k-int, --k-float, --k-char (new), --k-str. A char is always labelled 'str · length 1', because Python has no char type.

NARRATION RULE: fields marked (narration) do not count as a different picture in sameProp. Two props that differ only in those fields are the same picture, so if F1 keeps the layer's key across such beats, the element stays and the change plays on it (the switch flips, the newcomer flies into its slot). Where an answer and a narration field disagree, the answer wins.

EXISTING (unchanged unless noted):
- { kind:'lamp', demo?:'on'|'off' }: a lamp on a switch. True lights it; a str is stuck on as a note and lights nothing. NEW demo (narration): forces the switch for a beat, 'on' flipping it to True and lighting the lamp, 'off' flipping it back. It only applies while there is no answer. Use for 1b beats 4–7 and the ask 'Turn the lamp on'.
- { kind:'fish' }: is a fish a bird? False gives ≠, True draws wings. NEW: a str answer ("no") is drawn as a note stuck on the fish, and nothing else changes (the sign still says '= ?'). For the 1c miss.

NEW demo (narration): 'count' drops the apples in one at a time while a counter beside the basket rolls 1, 2, 3 in whole steps only; 'half' has half an apple land on the rim and bounce off while the counter stays and shakes. For 1b beats 9–10, e.g. {kind:'basket',apples:3,demo:'count'} then demo:'half'.

The robot stands in front of them, and the stage clips them at its edge. For 1a beat 4, label 'your instructions go here'.
- { kind:'lamps', on:number }: 1 to 4 lit lamps, each over a True pill, joined by '+'. Each True then drops down as an int 1, and '= n' pops out, tagged int. For Level 2's True + True.
- { kind:'codes', chars:string }: each distinct character (up to 8) slides in from the left onto a number line at its code, and the code is written under its tick. Codes within 10 of each other are spaced by value, so a gap in the codes shows; wider spreads are spaced evenly in code order. For Level 2's ord, e.g. 'ABC'.
- { kind:'scale', parcels:number, each:number }: before a numeric answer, the parcels (at most 12, each labelled 'N kg') wait on the floor two abreast and the readout says '? kg'. With the answer they drop onto the platform one by one, three abreast, then the readout shows '<answer> kg'. A reading that is not parcels × each turns the readout amber. The scale fills its slot (the readout is the widest thing in it, 15px type) so the kg can be read at the slot's size. For the order level.
- { kind:'code', text:string, mark?:number }: a short Python block on a card, monospace, indentation kept, with a faint dotted guide down each indented run so "inside the `for`" is seen. For a "read it before you run it" beat: show the block from the beat that introduces it through the ask, so the learner predicts from code, not from a sentence about code (R1). `text` is the block with `\n` between lines; tabs become four spaces, blank lines at either end are dropped and the indent every line shares is removed, so an indented template literal reads flush. At most 8 lines (CODE_LINES); a ninth becomes `…`. The type is as large as the longest line and the line count allow (codeSize, capped at 16 units), so keep lines short: a two-line loop of ~20 characters reads at about 12px on a desktop stage; 30+ characters or 6+ lines gets small on a phone. Keywords, strings (str colour), numbers (int colour) and comments are coloured; nothing else is changed. `mark` (narration) highlights one line, counted from 1; a later beat with another `mark` slides the highlight and the card stays. TWO RULES FOR A MISS, one per case, so that what the picture shows always agrees with what the crow says:

A REFUSED ANSWER (refused). A miss that the picture would draw the way it draws the right answer is drawn *refused*: still what the robot thought, but in amber, in the picture's own idiom, and the layer gets data-refused="yes". `looksRight(view)` says, per picture, whether an answer is drawn like the one the picture asks for (the lamp lit or darkened by any bool; the basket counted to its apples, so `3.0` or `2 + 1` in a basket of three; the lift parked on a floor it has, so `-1.0`; the egg box full; every crate's bolts lit; the tiles making what the sum makes; and so on — its doc comment lists them all), and `refused(view)` is `verdict === 'miss' && !unworked(view) && looksRight(view)`. The answer tag is outlined in amber with no ✓, and the sentence adds that the robot's answer is not the answer yet. Right answers and honest misses (a wrong number drawn as itself) are unchanged. (The doorway: any bool. The note: its own words.) A new picture kind that can draw a miss as a yes needs a case in looksRight.

A REFUSED RIGHT NUMBER (unworked). When a step's verdict is 'miss' and the answer equals the number the picture asks for (rightNumber: crates crates × each, bolts have − use, share litres / robots, scale parcels × each, packs packs × sum(each) + loose, expr the last of `then`, letter the char's code, numberline its `want`, tiles the number its sum makes), or the words it asks for (rightText: tiles, what a sum of words glues or repeats into, so `"botgineer"` typed whole waits under an amber `= ?`), the answer was typed by hand or reached the wrong way, and the reply is refusing it. The picture then draws nothing as answered: no bolts lit or ringed, no oil poured, parcels left on the floor, no working shown, the tile not turned, no marker. In their place is an amber '?' where the working would go ('7 * 6 = ?', '20 - 7 = ?', '? kg', '"M" → ?'), dashed amber outlines, and the answer tag keeps the value with an amber '?' instead of a ✓. The layer gets data-worked="no" and the sentence says it has not been worked out yet. Compared by value, so a typed 4 for 8 / 2's 4.0 counts. A wrong number is drawn as itself, as before. A picture that asks for a worked-out number and is not in that list needs a case in rightNumber (and a `want`-style field if the number is not implied by the prop).

LAYERING. The props slot has no z-index and comes before the cast in the stage's markup, so a picture always paints behind every actor: a picture that reaches past its slot, or a phone-width stage where the slot overlaps a character, goes behind a face, never over it.
